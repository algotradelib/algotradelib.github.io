Detailed Description

The asynchronous KIS REST client: market data, account inquiries and orders for domestic stocks.

It requests an access token when first needed and shares one refresh among concurrent requests. Sends custtype P. KIS's field reference reads B : 법인 / P : 개인, and its token guide (접근토큰발급) groups 일반개인고객 and 일반법인고객 under the one-day client-credentials token, apart from 제휴법인 (a three-month token by authorization code, and personalseckey, 제휴사 회원 관리를 위한 고객식별키). The partner-corporation flow (custtype B) is not supported. Create it with std::make_shared. Each completion runs on the handler's associated executor, or on the client's strand if it has none. A blocking wrapper is KisBlockingClient.

Uses a token issued earlier for the same app key and environment instead of requesting one.

The client does not request a new token when KIS refuses the adopted one: each request fails with KIS's code until five minutes before the adopted expiry. The token does not identify its key, so key stored tokens by environment and app key, and discard one KIS refused.

Call it on the client's strand or before any request; on the blocking client, between calls.

Parameters
tokenThe token.
Returns
false (nothing adopted) if the token is empty or expires within five minutes.

CompletionToken && token )

Requests bars, reading KIS pages until count_ bars are collected.

Every bar is stamped at its open: a minute bar at the start of its minute. Paging stops early after 50 pages, when a page returns no bars, or (for minutes) at the start of the trading day. A period page asks for a date window of 100 bars' worth of calendar days, so an empty one means KIS has no older bars or none in that window (a halt longer than the window). A series may therefore be shorter than count_ for any interval; then, unless it is empty, next_cursor_ is set to continue from, since an empty page does not prove the history exhausted.

Cancels an order (all or part of it, as amendment says).

After an error of unknown outcome (see async_place_order) the order may still rest.

One refusal is recognized as one, on a demo account only: the demo server's 40330000 (nothing left to amend or cancel), in an HTTP 200 reply that carries no new acknowledgement, is INVALID_ARGUMENT with reached_broker_ set. It says the cancellation did nothing, not what became of the order: it may have filled. The same reply from the real server stays PROTOCOL, as does every other refusal of a cancellation this client does not classify further (a rate-limit code is RATE_LIMIT).

◆ async_place_order()

template<typename CompletionToken>
auto algotradelib::kis::KisClient::async_place_order ( KisAccount account,
OrderRequest order,
CompletionToken && token )
inline

Places a cash order.

The request is never resent. After an error for which runner::outcome_of returns INDETERMINATE (BrokerError::reached_broker_ set and a category of TRANSPORT, CANCELLED or PROTOCOL, or HTTP with a status of 500 or more), the outcome is unknown. That includes a 200 reply KIS marks as failed (rt_cd not 0, such as insufficient balance) and this client does not recognize, which it reports as PROTOCOL; a rate-limit code there is RATE_LIMIT, which runner::Runner keeps for a later pass. Read async_open_orders or async_order_history before placing again, since KIS has no idempotency key.

Some refusals are recognized as refusals, each from its own server only: the demo server's 40240000 (nothing held to sell), 40570000 (the market has not opened) and 40580000 (the market has closed), and the real server's APBK3061 (during the after-market session, only after-market order types are accepted). In an HTTP 200 reply that carries no acknowledgement, each is INVALID_ARGUMENT with reached_broker_ set, which runner::outcome_of reads as REJECTED. A demo code from the real server, or the real code from the demo server, stays PROTOCOL, as does every other refusal this client does not classify further (a rate-limit code is RATE_LIMIT, as above).

◆ token()

KisRest algotradelib::kis::KisClient::token ( ) const
inline

Returns the access token the client holds, to reuse in a later process (adopt_token).

KIS issues one token per app key per minute (EGW00133), so a program that runs once per action can act only once a minute unless it keeps the token. The token is a bearer credential: store it as carefully as the key and secret.

Read it on the client's strand or before any request; on the blocking client, between calls.

Returns
The token, empty until a request has obtained one.
