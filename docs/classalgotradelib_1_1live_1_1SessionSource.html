Detailed Description

template<typename Session, typename Journal = runner::MemoryJournal, typename MarketData = Session>
class algotradelib::live::SessionSource< Session, Journal, MarketData >

The source a runner::PollingLoop polls: reads a broker session and feeds bars, quotes, holdings, orders, buying power, price bands and the calendar to a runner.

Bars: each poll reads every instrument, then feeds the bars not fed before in period-end order across instruments. A bar whose period has not ended by the later of Runner::observed_at() and the series' receipt time is left for a later poll (a daily bar read during the session waits); this check applies to close-stamped bars and to daily and minute bars, and only once either instant is known (open-stamped weekly, monthly and yearly bars are fed unchecked). Of the bars collected, only each instrument's newest (which may be yesterday's, if today's is still forming) is fed live, and only if it ended strictly after every older bar collected in the same poll, of any instrument (a tie is history; instruments' newest bars are not compared with each other). The rest go through Runner::feed_warmup, so a restart does not act on the history it reads. This does not make the newest bar recent.

Requests are tagged by kind, so a client budget with a trading reserve (network::RateLimitBudget::trading_reserve_) keeps capacity for orders. A kind the broker does not offer compiles to no request and returns UNCHANGED. A failed poll leaves the previous calendar, buying power and price bands in place.

With a journal (set_journal), every order listing is also checked against the instructions the journal holds as unresolved, resolving them in the runner's ledger where the broker's rows settle them.

Market data can come from a second session (MarketData): bars, quotes, price bands and the calendar are read from it, everything about the account from Session. For example, a KIS demo account cannot read the calendar, so it is read through a session built from a real account's keys and an empty KisAccount (which refuses every account request and order before any I/O).

Polls one kind of data and feeds or installs what arrived in the runner.

A poll is not atomic. Buying power and price bands ask for every currency or instrument even after one fails: the answers that arrived are installed, and the poll returns the failure (a failure outranks a rate-limit refusal). A quote poll stops at the first failure, with the quotes before it already fed. A bar poll that fails feeds nothing. A working-order poll installs the listing, reconciles, then feeds order updates, before it reads any history the runner needs; if that read fails it returns the failure with those effects kept. UPDATED does not mean journal reconciliation succeeded (see last_reconcile() and last_error()).

Template Parameters

Returns

Reads the broker's order list once, which lifts PollingLoop's startup hold.

Reads the working orders where the broker offers that inquiry; otherwise the whole order history (all pages, or the read fails). A broker with neither does not compile. The listing is adopted as the starting state: orders already resting produce no order updates, and one that fills or is cancelled before the first working-order poll produces none either.
