A runner that sends nothing: handlers fire and instructions are recorded by a RecordingExecutor.

◆ JournalOutcome

enum class algotradelib::runner::JournalOutcome
strong

What a journal line says about an instruction.

PENDING is written before the instruction is sent; a later line with any other outcome answers it. A PENDING line with no answer means the process stopped while the request may have been in flight, so the order's existence is unknown.

Enumerator
PENDING 

Written before the send; whether the instruction exists is not yet known.

ACCEPTED 

The broker accepted the instruction; it exists.

REJECTED 

The instruction was refused, by the broker or before it was sent, so it does not exist.

The journal does not record who refused; a pass's report does.

INDETERMINATE 

The outcome is unknown (SendOutcome::INDETERMINATE: a failure in transit, an unreadable reply, an HTTP 5xx, or a broker refusal reported as PROTOCOL).

RESOLVED 

A recovery sweep read the broker's order list and closed the question.

order_id_ is set if a matching order was found and empty if none was; detail_ says what was seen. For a cancellation, a match means the named order was in the listing read (resting only if that listing held working orders alone); it does not mean the cancellation completed.

CONFIRMED 

A serialized runner accounted for the placement: holdings showed what it filled, its history showed it ended with nothing filled, or an operator released it.

baseline_ is the instrument's holding afterwards, where holdings showed it; detail_ says which. See Runner::allow_overlapping_orders.

HELD 

Evidence contradicted the placement (holdings moved past what it can explain), so only an operator may account for it (Runner::release_obligations). Written with requires_operator_.

◆ MatchVerdict

enum class algotradelib::runner::MatchVerdict
strong

What the broker's order list says about one instruction of unknown outcome.

A missing row means NOT_PLACED only after the matching window has closed (the listing may lag an accepted write); before that it is UNDECIDED. NOT_PLACED is a finding about the rows supplied, not the broker's word that no order exists: an overlapping runner then forgets the placement, and a serialized runner (Runner::serialized) keeps it owed.

Enumerator
MATCHED 

Exactly one row corresponds; the order exists.

For a cancellation: the named order is in the listing supplied (which may include history, so not necessarily resting).

NOT_PLACED 

No row corresponds and the window has closed: no order was found.

For a cancellation: the named order is not in the listing supplied.

AMBIGUOUS 

Several rows could correspond, a row that fits is another placement's, or a row that fits cannot be confirmed; the instrument stays withheld until a later sweep or an operator decides.

UNDECIDED 

No row yet, and the window is still open; wait for the next sweep.

NEEDS_OPERATOR 

The instruction came from a damaged journal line, or its line cannot be matched (unresolvable_reason); only an operator may resolve it.

◆ SendOutcome

enum class algotradelib::runner::SendOutcome
strong

What became of one instruction (a placement or a cancellation) an executor was asked to send.

A request of unknown outcome (INDETERMINATE) is never replayed automatically: the runner places nothing more for that instrument until the broker's order list is read and the instrument resolved, though a named cancellation may still go. (A request known not to have reached the broker, or refused for its rate limit, can be offered again; see Runner::retry_retained_targets.)

For a cancellation, ACCEPTED means the request was accepted, not that the order is gone, and a refused cancellation leaves the order as it was (resting, or filled meanwhile).

Enumerator
ACCEPTED 

The broker accepted the instruction (for a placement, the order exists).

REJECTED 

The broker refused the instruction (for a placement, the order does not exist); nothing needs reconciling.

INDETERMINATE 

The outcome is unknown (see outcome_of): the request failed in transit or was cancelled, the reply could not be read, the broker answered with an HTTP 5xx, or its answer is reported as PROTOCOL.

At KIS (an unrecognized reply with rt_cd not 0, such as insufficient balance), Toss (any refusal but a rate limit or a refused token) and Kiwoom (a return_code outside its documented error list) the broker's own refusals are reported as PROTOCOL, so they land here, not in REJECTED. The exception is the few order refusals the KIS and Kiwoom clients recognize (most from their demo servers, three from their real servers), which are REJECTED. Nothing more is placed for that instrument until the broker's order list has been read and the instrument resolved.

UNAVAILABLE 

Local machinery failed (such as the order journal not being writable), so nothing was sent.

The runner stops sending (strategy::HaltReason::LOCAL_FAILURE) until Runner::resume_after_local_failure, since every later order would fail the same way.

REFUSED_LOCALLY 

The binding refused the instruction before sending it (such as an idempotency key at a broker without one, or a cancellation of an order the broker has no reference for).

No request was counted against the rate limit (for a placement, the order does not exist), and the runner keeps trading.
